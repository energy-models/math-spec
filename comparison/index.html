Three ways to say a lookup that a single arrow cannot

#422 settled that a lookup maps into a declared dimension. What it left open is every map that needs more than one column on each side: a zone that changes by period, a line with two ends, a table read from either key. Three pull requests answer that. Four of the five models below are sayable under all three, so the difference is mostly what the file declares and what a call has to name — until the fifth, which only one of them can say at all.

Which one you have, in three questions

  1. Does each thing have exactly one? Then it is a map. Give the lookup a key, and the language will hold the data to it.
  2. Is there a number on the pair? Then it is a parameter. The number's own rows are the pairing, and a lookup would repeat it.
  3. Are both sides the same kind of thing? Then only #437 can say it. A parameter cannot name one dimension twice, so there is no fallback.

A flag cannot be multiplied — so a table of ones must be dtype: int

Constraint 'reserve': 'eligible' is declared dtype: bool, and an expression is arithmetic — only dtype: float and dtype: int bind a column it can be done to. A flag masks rather than scales: name it in a where ("eligible", "NOT eligible"), which is what a mask is — or declare it dtype: int where the 0/1 is meant to arrive as data and be multiplied by.

The workaround for an unweighted pairing is to multiply by ones. The honest dtype for a flag is refused in arithmetic, so the ones have to be declared as numbers.

A buddy is refused on #433 alone — #436 is the stacked draft that lifts it

Lookup 'rep_of' maps 'snapshot' into itself. A lookup maps into a different dimension.

Measured on #433's head. On #436's head the same file loads.

And the rewrite #436 prescribes for neighbours — measured on #436's own branch

Parameter 'adjacent' names dimension 'region' twice. A frame is a product of distinct dimensions.

#436's description sends an undirected neighbour relation to “a parameter over [bus, bus]”. That file does not load, on that branch or any other. It is the fifth model below.

1demands a map that varies along a second dimension

A generator bids in a zone, and the zone changes by period

Zonal demand must be met by the generators bidding in that zone. Which zone a generator bids in is not fixed: it is agreed per investment period. So the map from generator to zone is read at a period as well as at a generator. This is the case #161 opened, and the one all three proposals were written for.

$$ \sum_{g \in \mathcal{G} \,:\, \mathrm{zone\_of}(g,\ e) = z} p_{g,e} \ge \mathrm{demand}_{z,e} \qquad \forall\, z \in \mathcal{Z},\ e \in \mathcal{E} $$

The math is the same under all three proposals. Only the name of the map changes, so the file is what the choice is about, not the printed model.

3demands two columns over one dimension

Nodal balance, where a line has two ends

Flow leaves one bus and arrives at another, so a line carries two bus labels. The balance at a bus sums generation there, plus flow arriving, minus flow leaving. The guard below drops any line whose two ends are the same bus.

$$ \sum_{g \in \mathcal{G} \,:\, \mathrm{gen\_bus}(g) = b} p_{g,e} + \sum_{l \in \mathcal{L} \,:\, \mathrm{ends.bus1}(l) = b} f_{l,e} - \left( \sum_{l \in \mathcal{L} \,:\, \mathrm{ends.bus0}(l) = b} f_{l,e} \right) = \mathrm{load}_{b,e} \qquad \forall\, b \in \mathcal{B},\ e \in \mathcal{E} $$
$$ f_{l,e} \le 10 \qquad \forall\, l \in \mathcal{L},\ e \in \mathcal{E} \,:\, \mathrm{ends.bus0}(l) \neq \mathrm{ends.bus1}(l) $$

The math is the same under all three proposals. Only the name of the map changes, so the file is what the choice is about, not the printed model.

5demands a relation between two members of one dimension

Which regions are neighbours

A region is capped on what its neighbours produce. Neighbourhood is symmetric and carries no number: two regions touch, or they do not. Both columns of the relation are regions, and that is what makes this case different from every one above.

$$ \sum_{r' \in \mathcal{R} \,:\, \left( r,\ r' \right) \in \mathrm{adjacent}} x_{r',p} \le \mathrm{cap}_{r,p} \qquad \forall\, r \in \mathcal{R},\ p \in \mathcal{P} $$

A sum that lands where the expression already is

A load-weighted sum of generation at each bus reads load at the bus the generator sits on, and lands on that same bus. Today the language refuses it, because bus would be needed twice. Under relations the produced column is joined on instead, and the sum is masked. This is not one of the five problems, and it is the one capability difference they do not show.

?what the choice turns on

Three questions, one per column

Four of the five models are sayable under all three proposals, so capability alone does not decide this: the two narrower proposals reach the same math with more declarations. What differs is where the file puts a fact, and what a reader of a call has to already know. The fifth model is the exception, and the only place a column is simply empty.

per: conditioning

The map keeps its arrow, and the call site is untouched: by=zone_of means what it means today. The direction is a property of the declaration, so a table read both ways is declared twice, and the language does not know the two are one table.

Is a call that names nothing worth a declaration per direction?

keys and a dot

One declaration per table. The key list is the cardinality claim, and the dot names which key a call walks. A column is named after its dimension, so a table cannot hold two columns over one dimension — a line's two ends stay two lookups.

Is one new token at the call site the whole price worth paying?

relations

A lookup is a table of named columns, and key: is the only claim the data can be held to. Every direction is the call's, named by from= and into=. It says everything above and more, at ten rules, two keywords and a rewrite of every declaration in the tree.

Does the language want a relation, or a map?
